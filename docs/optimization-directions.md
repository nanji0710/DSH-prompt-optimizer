# 提示词优化方向（v0.2 重设计）

> 基于 v0.1.3 实测反馈重写。核心原则：**输出必须能直接用，不能有任何 TODO 占位符；篇幅不能比原文膨胀 3 倍以上；要真正帮用户把口语诉求翻译成可执行指令，而不是贴标签或套模板。**

---

## 一、实测暴露的三个问题

### 1.1 本地规则优化：只贴标签，不做抽取

v0.1.3 本地引擎对"拼多多的GMV，去退数量，成本。京东自营的去退数量，成本。结果表和底表有一点差异，你查一下"的输出：

```
【角色设定】
你是资深后端开发工程师...
[原文原样贴在下面]
```

**问题**：
- 没有抽取实体（拼多多、京东自营）
- 没有抽取指标（GMV、去退数量、成本）
- 没有识别动作（查差异、对账）
- 没有结构化，原文一个字没动

这不是优化，是加了个前缀。

### 1.2 LLM 优化：占位符 + 过度膨胀

LLM 输出的问题：
- 出现 6 处 `[待补充:表名]`、`[待补充:时间范围]`、`[待补充:字段口径]` 占位符——用户要的是能用的提示词，不是带 TODO 的半成品
- 从 1 行膨胀到 50 行，五段式模板（任务目标/背景/具体要求/约束/输出格式）对短诉求过重
- 大量通用套话（"只做差异排查与原因定位，不修改线上数据"），这些对一个"查一下差异"的诉求没有增量价值

### 1.3 WorkBuddy 的优点

```
优先排查拼多多 GMV 的差异：结果表与底表的数值相差 28.07，
已知底表数据正确，结果表数值偏大。
请定位导致结果表多出 28.07 的具体原因，说明差异产生的环节或逻辑，
并给出修正方案。
```

**好在哪**：
- 3 行，紧凑
- 直接给具体动作（定位原因 + 给修正方案）
- 没有任何占位符
- 没有套话

## 二、重新设计的优化原则

| 原则 | 说明 |
|------|------|
| **零占位符** | 输出里绝对不能出现 `[待补充]`、`TODO`、`xxx`、`<填这里>` 这类标记。缺失的信息要么不写，要么写成"请自行判断/按常规处理"。 |
| **篇幅克制** | 优化后字数 ≤ 原文 × 3。原文 100 字，输出不超过 300 字。超过就说明在套模板。 |
| **信息抽取优先** | 先从原文抽出实体、指标、动作、约束，再按紧凑模板重组。不是贴角色标签完事。 |
| **动作导向** | 输出必须以"你要做什么"开头，而不是"我是谁"。角色设定如果不能改变输出行为，就不要。 |
| **缺信息不问** | 本地引擎不反问用户（那是交互层的事）。缺表名就写"你知道表名的话直接用"，不写占位符。 |
| **LLM 也要克制** | 调 LLM 优化时，system prompt 必须明确禁止占位符和套话。 |

## 三、本地规则优化（重设计）

### 3.1 流水线（从 4 级砍到 2 级）

```
原文
  │
  ▼
Step 1: 信息抽取（实体、指标、动作、场景）
  │
  ▼
Step 2: 紧凑重组（不超过 3 段，每段 2-3 行）
```

砍掉 v0.1.3 的 L0 客套清除和 L2 通用约束补全——实测发现这些对短诉求几乎没有增量，反而增加篇幅。

### 3.2 Step 1：信息抽取

从原文用正则/关键词匹配抽取 4 类信息：

**A. 动作识别**（用户要模型干什么）

| 关键词 | 抽取到的动作 |
|--------|------------|
| 查、看看、排查、找一下、对一下、核对 | 「排查并定位问题」 |
| 写、生成、帮我写 | 「产出」 |
| 总结、概括、缩 | 「总结要点」 |
| 翻译、译 | 「翻译」 |
| 为什么、怎么回事、啥原因 | 「解释原因」 |
| 改、修改、优化、重构 | 「修改并给出新版本」 |

**B. 实体抽取**（涉及哪些对象）

- 平台/公司：拼多多、京东、淘宝、抖音、快手、天猫、唯品会、得物、小红书
- 业务模块：GMV、去退数量、去退金额、成本、退款、退货、客单价、转化率
- 数据表：结果表、底表、明细表、汇总表、日报、周报
- 技术栈：React、Vue、Python、Java、MySQL、SQL、Excel、Pandas

**C. 场景识别**（这是什么类型的任务）

- 数据对账/差异排查（出现"结果表 vs 底表"、"对不上"、"差异"）
- 代码开发（出现"报错"、"bug"、"功能"、"接口"）
- 文档写作（出现"方案"、"PRD"、"周报"、"汇报"）
- 问答（出现"为什么"、"怎么"、"如何"）

**D. 约束抽取**（用户已经说了哪些限制）

- 时间范围：最近 7 天、本月、Q3、2024 年
- 范围限定：只看拼多多、不包括测试数据
- 输出要求：表格、代码、300 字以内

### 3.3 Step 2：紧凑重组

根据抽取结果套最匹配的**一个**模板（不是五段式，是单段或两段）。

**模板 1：数据对账/差异排查**（最常用）

```
请排查以下数据差异并定位原因：

涉及平台与指标：<抽取到的平台×指标列表，用顿号连接>
对比对象：<结果表/底表/明细表>
已知现象：<用户原文描述的异常>

要求：
- 先给出差异出现在哪个环节（取数口径 / 计算逻辑 / 关联聚合 / 调度时效）
- 每个原因给一条可验证的 SQL 或检查方法
- 最后给修正建议，不要改线上数据
```

**模板 2：代码/开发**

```
请帮我处理以下开发任务：

<用户原文>

要求：
- 给完整可运行代码，标注语言
- 关键逻辑加注释，不要逐行解释
- 如果有多种实现，给推荐方案 + 一句话理由
```

**模板 3：文档/写作**

```
请帮我写：<用户原文核心诉求>

要求：
- Markdown 格式，结论先行
- 不超过 500 字
- 缺失的背景按常规处理，不要反问
```

**模板 4：问答/解释**

```
请回答以下问题：<用户原文>

要求：
- 先给一句话结论
- 再分 2-3 点解释
- 不确定的地方直接说"不确定"，不要编造
```

**模板 5：兜底（抽不出任何类型）**

```
<用户原文，仅做客套清除>

要求：直接回答，不要反问，缺失信息按常识处理。
```

### 3.4 角色设定：默认不注入

v0.1.3 默认注入"你是资深后端工程师"——实测这对数据对账任务没有帮助（用户要的是 SQL 排查，不是后端架构）。

改为：
- **默认不注入角色**
- 用户手动选了角色才注入，且角色设定压缩到 1 行（不是 5 行）
- 角色模板示例："你是一名数据分析师，回答时先给结论再给依据。"

## 四、LLM 深度优化（重设计）

### 4.1 给 LLM 的 System Prompt（核心）

```
你是一名提示词优化专家。请把用户的原始提示词优化成可以直接喂给大模型的高质量版本。

严格遵守以下规则：
1. 绝对不要出现 [待补充]、TODO、xxx、<占位符> 这类标记。缺失的信息要么不写，要么写成"按常规处理"。
2. 优化后总字数不超过原文的 3 倍。短诉求就短输出，不要套五段式模板。
3. 输出必须是"可执行的指令"，以动词开头（请排查/请写/请总结），不要写"我将..."这类自我描述。
4. 只保留对回答质量有实际影响的约束。删除"不要编造、用中文回答"这类大模型本来就会做的事。
5. 如果原文已经很清晰，直接返回原文，不要为了优化而优化。

输出格式：直接给优化后的提示词，不要解释你改了什么。
```

### 4.2 为什么这样改

| v0.1.3 的问题 | v0.2 的对策 |
|--------------|-----------|
| 出现 6 处【待补充】 | 规则 1：绝对禁止占位符 |
| 1 行原文膨胀到 50 行 | 规则 2：字数 ≤ 3 倍 |
| 五段式模板（任务/背景/要求/约束/格式） | 规则 5：原文清晰就返回原文 |
| 大量套话 | 规则 4：只保留有实际影响的约束 |
| 输出里夹着"我将..." | 规则 3：必须是可执行指令 |

### 4.3 优化后的预期输出（用同一条原文测试）

**原文**：拼多多的GMV，去退数量，成本。京东自营的去退数量，成本。结果表和底表有一点差异，你查一下

**LLM 优化后应该输出**（约 100 字）：

```
请排查结果表与底表的数据差异，涉及拼多多（GMV、去退数量、成本）和京东自营（去退数量、成本）。

要求：
1. 定位差异出在取数口径、计算逻辑、关联聚合还是调度时效
2. 每个怀疑方向给一条可验证的 SQL
3. 最后给修正建议，不要改线上数据
```

对比 v0.1.3 的 50 行输出——没有占位符、没有套话、没有五段式模板、字数在合理范围。

## 五、本地 vs LLM 的分工

| 场景 | 用本地规则 | 用 LLM 优化 |
|------|-----------|------------|
| 原文 < 50 字，结构简单 | ✅ 模板 1-5 直接套 | ❌ 过度膨胀 |
| 原文 > 200 字，逻辑复杂 | ❌ 正则抽不全 | ✅ LLM 能理解语义 |
| 用户要快速改一下直接用 | ✅ 毫秒级 | ❌ 等 API 响应 |
| 用户愿意等几秒换更好的 | ❌ | ✅ |
| API 未配置 | ✅ 必须本地 | ❌ |

**默认策略**：本地规则兜底（永远可用），用户主动点"深度优化"才调 LLM。

---

## 六、验收标准（v0.2 必须通过）

1. 输出里 grep 不到 `待补充`、`TODO`、`xxx`、`<.*?>` 任何占位符
2. 100 字以内的原文，优化后不超过 300 字
3. 原文已经很清晰时，输出接近原文（不强行加结构）
4. 数据对账类任务，输出必须包含"定位环节 + 验证方法 + 修正建议"三要素
5. 默认不注入角色（用户选了才加，且只加 1 行）
6. 本地引擎响应 < 50ms，LLM 优化失败时自动降级到本地结果
