> 保留本文档仅作变更记录（实现见 `src/local-optimizer.ts`，现行两级流水线：信息抽取 → 紧凑重组）。

## 一、设计原则

| 原则 | 说明 |
|------|------|
| **只做确定性变换** | 每条规则必须能靠正则或字符串匹配落地，不允许"让模型自己悟"。同一段输入永远输出同一段结果。 |
| **保留用户原意** | 不删用户的核心诉求，只去客套、补结构、加约束。**删掉的每一个字都必须能证明它不携带任务语义。** |
| **宁可漏删，不可误删** | 规则拿不准时**放弃本次变换**（回滚），而不是猜。误删一个"大概"就篡改了用户对精度的要求。 |
| **分级递进** | 从最安全的清洗（L0）到最激进的角色模板（L3）逐级叠加，每级可独立开关。 |
| **中文优先** | 规则同时覆盖中英文口语，但默认输出中文格式。 |
| **失败即降级** | 任何规则匹配异常都跳过该条（`try/catch` 单条包裹），不中断流水线，保证插件永远可用。 |
| **代码块免疫** | 用户贴进来的代码（``` 围栏内、行内 `` ` `` 内）默认只做空白类清洗，**绝不做标点/列表/分段改写**。 |

### 1.1 三条质量不变量（实现完成后必须逐条自测）

| 不变量 | 内容 | 校验方式 |
|--------|------|----------|
| **I1 幂等** | `optimize(optimize(x)) === optimize(x)` | 对测试集每条跑两遍比对 |
| **I2 非空** | 输入非空 ⇒ 输出非空 | `"你好"`、`"嗯"`、`"。。。"` 等极端输入 |
| **I3 语义单调** | 输出不得删除原文中的**数字、专有名词、否定词、量词、不确定性词** | 用第 12 节的反例集回归 |

> I3 是硬约束：`"大概 3 天做完"` 里 `大概` 和 `3` 都属于不可删除信息，任何规则序列删掉它们都算 bug。

### 2.4 正则书写公约（★照此写，否则会踩坑）

1. 一律用 JS 原生正则。需要 `^`/`$` 匹配**每一行**行首行尾时加 `m`；只作用于**整个输入首行**的规则（L0-010/L0-011/L0-014）**不要加 `m`**，改用"切出 `lines[0]` 单独处理再拼回"的方式（见 L0-010 的行边界锚点说明）。
2. **禁止用 `\s` 做普通空白的字符类**——`\s` 含 `\n`，会把段落结构吃掉。空白要用显式的 `[ \t]` 或 `[ \t\u3000]`。
3. `replace` 必须带 `g`，否则只替换第一处。
4. 禁止嵌套量词（如 `(\s*)*`、`(a+)+`），避免灾难性回溯；量词尽量加边界（`{1,3}`、`{4,}`）。
5. 需要 lookbehind 时优先改写成**捕获组 + `$1` 回填**（lookbehind 在旧 Safari 不支持，客户端 bundle 会被 esbuild 原样输出）：`/(^|[\s，,])(?:嗯+)/g` → `'$1'`。
6. 每条规则用 `try { ... } catch { /* skip */ }` 单条包裹，`applied` 里只记录成功的规则 ID，异常推入 `failed`（便于排查"规则莫名不生效"——无效正则会静默失败）。

> **★ 两个"分析步骤"为什么排在这里**：`L1-001`（任务识别）与 `L2-001`（上下文抽取）都**不修改文本**，只是把结果存进 `Ctx`。把它们提前到所有改写规则之前有两个原因：
> ① `L2-001` 必须在 `L1-008` 之前——骨架里的【背景】槽位要用它的抽取结果；
> ② 两者都必须读**清洗后、结构改写前**的文本：`L1-002/L1-003` 会把并列项拆成多行，之后再抽取技术栈/规模会漏掉被拆散的信息。
> 因此实现时把这两个分析函数**在 L1 一开始就调用**，结果暂存，到用的时候直接取（不要把它们写成"在 L2 章节里才跑"）。

**顺序依赖的原因（写代码时必须理解，不要"优化"顺序）**

- L0-002 必须在 L0-003 之前：NBSP/全角空格换成半角后才会被"连续空白折叠"处理掉。
- L0-001 必须在 L0-003 之前：先 trim 行首，才轮得到行内折叠。
- L0-005 必须在 L0-012 之前：语气词删掉后会留下 `，，`，需要重复标点折叠来收尾（L0-012 内部还会再调一次）。
- L0-010/L0-011/L0-014 必须在 L0-012 之后、且包在收敛循环（L0-016）里：它们依赖"行首/行尾"边界，前面若还有规则插空行会破坏行边界判断；而 L0-010 删掉的"帮我"会**暴露**下一层客套（`"那个，帮我…"` → 删"那个" → 又出现"帮我"），只跑一遍删不干净，所以必须循环到不动点。
- L1-001 与 L2-001 必须在 L1-002 之前：两者都读"结构改写前"的文本，才能看到完整的并列项与上下文词。
- L1-002 必须在 L1-003 之前：`1) xxx` 与 `- xxx` 混排时，先统一序号再统一符号，缩进层级才不会错。
- L1-006 必须在 L1-007 之前：分段会改变行边界，标题识别必须看到最终行边界。
- L1-008 必须在 L1-007 之后：骨架重组要知道有哪些小节已经被识别出来了，避免重复造标题。
- L2-003 必须在 L2-002 之后：边界约束永远是文末最后一块，不能插到"输出格式"前面。

### 3.3 代码围栏分段器（所有"代码块内生效=否"的规则都必须经过它）

```ts
/** 把文本切成代码段与普通段，文本类规则只在 code:false 的段上执行。 */
function splitByFence(text: string): Array<{ code: boolean; value: string }> {
  const FENCE_OPEN = /^[ \t]{0,3}(?:```|~~~)/
  const parts: Array<{ code: boolean; value: string }> = []
  let buf: string[] = []
  let inFence = false
  for (const line of text.split('\n')) {
    const isFenceLine = FENCE_OPEN.test(line)
    if (isFenceLine && !inFence) {
      if (buf.length) parts.push({ code: false, value: buf.join('\n') })
      buf = [line]
      inFence = true
    } else if (isFenceLine && inFence) {
      buf.push(line)
      parts.push({ code: true, value: buf.join('\n') })
      buf = []
      inFence = false
    } else {
      buf.push(line)
    }
  }
  if (buf.length) parts.push({ code: inFence, value: buf.join('\n') })
  return parts
}
```

**行内代码（`` ` `` 包裹）保护**：对单行执行文本规则前，先把行内代码片段抽出换成占位符 `\u0000C0\u0000`、`\u0000C1\u0000`…，规则跑完再还原。凡是可能命中行内代码的规则（L0-005、L0-006、L1-002、L1-003、L1-006、L1-007）都必须走这一步。

```ts
function protectInlineCode(text: string): { text: string; restore: (s: string) => string } {
  const saved: string[] = []
  const masked = text.replace(/`[^`\n]*`/g, (m) => {
    saved.push(m)
    return `\u0000C${saved.length - 1}\u0000`
  })
  return {
    text: masked,
    restore: (s) => s.replace(/\u0000C(\d+)\u0000/g, (_, i) => saved[Number(i)] ?? ''),
  }
}
```

## 四、L0 清洗层

### L0-001 行首行尾空白清理 · 开关 `cleanWhitespace`

- **触发**：`/[ \t\u3000]+$/gm`（行尾）与 `/^[ \t\u3000]+/gm`（行首），合并为一条 `replace(/^[ \t\u3000]+|[ \t\u3000]+$/gm, '')`。
- **处理**：替换为 `''`。
- **作用域**：全段（含代码块，行尾空白无意义）。
- **正则要点**：**绝不能写成 `\s`**——`/^\s+|\s+$/gm` 会把整段空行也吃掉，破坏段落与代码块内的空行。

| 输入 | 输出 |
|------|------|
| `"  写个周报  "` | `"写个周报"` |
| `"\t需求：  \n  背景： "` | `"需求：\n背景："` |
| `"```\ncode  \n```"` | `"```\ncode\n```"` |

---

### L0-002 隐形字符归一 · 开关 `cleanWhitespace`

- **触发与处理**（三步，顺序执行）：

```ts
result = result
  .replace(/[\u00A0\u2007\u202F]/g, ' ')   // 不换行空格 → 普通空格
  .replace(/[\u200B-\u200D\uFEFF]/g, '')   // 零宽空格/连接符/BOM → 删除
  .replace(/\u3000/g, ' ')                 // 全角空格 → 普通空格
```

- **作用域**：非代码段。
- **理由**：从网页/微信/Word 复制来的文本常带 NBSP 与零宽字符，它们会让后续所有 `^`/`$`/空格规则失配，是最隐蔽的 bug 来源。

| 输入 | 输出 |
|------|------|
| `"需求\u00A0：\u200B写代码"` | `"需求 ：写代码"` |
| `"\u3000\u3000第一段"` | `"  第一段"`（随后被 L0-001 trim 掉） |

> 注意 `\u3000` 在中文里常当**段首缩进**用，转成半角后由 L0-001/L0-003 清理，符合预期。

---

### L0-003 连续空白折叠 · 开关 `cleanWhitespace`

- **触发**：`/[ \t]{2,}/g`
- **处理**：替换为 `' '`
- **作用域**：**非代码段**（Markdown 四空格缩进代码、YAML/JSON 缩进必须保留）。

| 输入 | 输出 |
|------|------|
| `"帮我  写   代码"` | `"帮我 写 代码"` |
| `"| 字段 |  类型  |"` | `"| 字段 | 类型 |"` |
| 代码块内 `"  const a = 1"` | 不变 |

---

### L0-004 连续空行折叠 · 开关 `cleanWhitespace`

- **触发**：`/\n{3,}/g`
- **处理**：替换为 `'\n\n'`（保留一个空行 = 一个段落分隔）
- **作用域**：全段（代码块内连续 3 个空行也无意义）。

| 输入 | 输出 |
|------|------|
| `"第一段\n\n\n\n第二段"` | `"第一段\n\n第二段"` |

---

### L0-005 重复标点折叠 · 开关 `filterPoliteWords`

- **触发**：`/([。，、；：！？,.!?;:])\1+/g`
- **处理**：替换为 `'$1'`（连续重复只保留一个）。
- **特例保护**：`……` 与 `——` 是合法中文标点，先处理再折叠：

```ts
result = result
  .replace(/(…){3,}/g, '……')     // 三点以上省略号 → 标准六点
  .replace(/(—){3,}/g, '——')     // 三个以上破折号 → 标准破折号
  .replace(/([。，、；：！？,.!?;:])\1+/g, '$1')
```

- **作用域**：非代码段；必须先抽出行内代码。
- **整行分隔线保护**：`---` / `***` / `___` 整行是 Markdown 分隔线，折叠会破坏文档结构。处理前先按 `^(?:-{3,}|\*{3,}|_{3,})[ \t]*$`（`gm`）把这类整行替换成占位符，规则跑完还原。

| 输入 | 输出 |
|------|------|

### L0-006 中英标点混用归一 · **实验规则，默认关闭**

### L0-010 句首客套清除 · 开关 `filterPoliteWords`

- **作用域**：**仅整个输入的第一条非空行**（后续行的行首不删，避免把正文里的"换个角度"之类删掉）。
- **触发**（逐个尝试，**命中一个即停**，本次调用至多删一块；多条命中由 L0-016 的循环继续处理）：
- **★ 行边界锚点**：因为只作用于首行，实现时先把文本按 `\n` 分成 `lines[0]` 与其余部分，只在 `lines[0]` 上跑这些正则，再拼回。**不要**给这些正则加 `m` 标志——加了 `m` 之后 `^` 会在每一行行首匹配，等于失去"仅首行"的约束（这正是旧实现 `:35` 的 bug 之一）。

```
/^(?:你好|您好|哈喽|嗨|在吗)[，,、!！。.~\s]*/
/^请问(?:一下)?[，,、!！。.~\s]*/
/^(?:麻烦|劳驾|拜托)(?:你|您)?(?:一下)?[，,、!！。.~\s]*/
/^(?:帮我|替我|给我)[，,、!！。.~\s]*/
/^(?:我)?(?:想|要)?(?:请教|问一下|咨询)(?:一下)?[，,、!！。.~\s]*/
/^(?:我想|我要|我打算)[，,、!！。.~\s]*/
/^(?:Hello|Hi|Hey)[,!.\s]+/i
/^(?:Could|Would|Can)\s+you\s+(?:please\s+)?/i
/^Please\s+/i
/^(?:I\s+want\s+you\s+to|I'?d\s+like\s+you\s+to)\s+/i
```

- **处理**：匹配块替换为 `''`，随后交回 L0-001 trim。
- **★ 长度守卫（关键）**：若删除后剩余长度 `< 4`，**回滚本次删除**。理由：`"你好，在吗"` 删完只剩空串，`"在吗，问个事"` 删完只剩 3 字，都不如保留原样。
- **为什么不用 `gim` 全局替换**：早期实现用了 `/^(麻烦|帮我|…)/gim`，会在每一行行首都删"帮我"，把
  `"第一段\n帮我确认这点"` 改成 `"第一段\n确认这点"`——虽然不算错，但会让"用户明确写的诉求主体"消失，且无法回滚。**只处理首行更安全。**

| 输入 | 输出 | 说明 |
|------|------|------|
| `"你好，帮我写个请假条"` | `"写个请假条"` | 命中第 1 条，剩余 6 字 |
| `"请问怎么写周报"` | `"怎么写周报"` | 命中第 2 条 |
| `"麻烦你帮我看看这个 bug"` | `"看看这个 bug"` | 第 3 条删"麻烦你" → 循环第二轮第 4 条删"帮我"（见 L0-016） |
| `"在吗，问个事"` | `"在吗，问个事"`（不变） | 长度守卫回滚 |
| `"Hi, write a function"` | `"write a function"` | 英文分支 |
| `"请你评估这个方案的风险"` | `"评估这个方案的风险"` | 可接受：`请你` 不携带任务语义 |

**反例（必须保留）**

- `"我想了解一下这个接口的鉴权方式"` → 若删掉"我想"剩"了解一下…"尚可；但**不要**删成"了解这个接口的鉴权方式"以外的形态。规则里 `^(?:我想|我要|我打算)` 只删这三个词，不要连"了解"一起删。
- `"帮我看看这个 bug 是不是并发导致的"` → 只允许删"帮我"，**不允许**删"看看"（那是动作强度）。
- 任何情况下**不删"请"**（单独出现的 `请` 保留）：`"请用中文回答"` → 不变。

### L0-011 句尾客套清除 · 开关 `filterPoliteWords`

- **触发**：`/[，,、\s]*(?:谢谢|多谢|感谢|拜托了|辛苦了|麻烦你了|thanks|thank you|please)[。.!！~\s]*$/i`
- **处理**：删除匹配块（只删**最后一处**，不用 `g`）。
- **★ 守卫三条**：
  1. 删除后剩余长度 ≥ 4（同 L0-010）。
  2. 匹配起点前一个非空白字符**不是引号**：`"'「『`"`\`——避免删掉引号内的"谢谢"（用户可能让你写一段感谢信）。

| `"总结一下这篇文章，辛苦了"` | `"总结一下这篇文章"` |

### L0-012 语气词清除 · 开关 `filterPoliteWords`

**★ 分三档，只有 A 档自动删，B 档严格受限，C 档永不删。**

#### A 档：孤立填充词，直接删

- **触发**：

```ts
const FILLER = /(^|[\s，,。.；;：:!！?？、])(?:嗯+|啊+|呃+|哦+|唉+|额+|em+|hmm+|uh+)(?=[\s，,。.；;：:!！?？、]|$)/gim
result = result.replace(FILLER, '$1')
```

- **处理**：替换为 `'$1'`（保留前导边界字符）。**用捕获组回填而不是 lookbehind**，兼容旧 Safari。
- **后置清理**（删完必然留下孤立标点）：

```ts
result = result
  .replace(/([，,、；;：:])\s*(?=[，,、；;：:])/g, '')   // 连续标点只留最后一个
  .replace(/^[\s，,、；;：:]+/, '')                    // 行首孤立标点
```

| 输入 | 输出 |
|------|------|
| `"嗯，那个，帮我看看嗯"` | `"，那个，帮我看看"` → L0-005 收拾 → `"那个，帮我看看"` |
| `"啊这，怎么改"` | `"这，怎么改"` |
| `"这个方案 emmm 不太行"` | `"这个方案不太行"` |
| `"啊哈，原来如此"` | 不变（`啊` 后是"哈"，不在边界类内） |
| `"天啊，怎么会这样"` | 不变（`啊` 前是"天"，不在边界类内） |

#### B 档：插入语，**仅在句首且后接逗号且剩余 ≥ 10 字**时才删

- 词表：`那个`、`就是`、`然后呢`、`对吧`、`你懂的`、`这个这个`
- **触发**：`/^(?:那个|就是|然后呢)[，,、]/`（仅限**整段第一行行首**）
- **处理**：删掉该插入语与逗号，剩余 < 10 字则回滚。

| 输入 | 输出 | 说明 |
|------|------|------|
| `"那个，帮我写个排序算法"` | `"帮我写个排序算法"` | 剩余 8 字 < 10 → **回滚** |
| `"那个，我需要你帮我梳理一下整个下单流程的异常分支"` | `"我需要你帮我梳理一下整个下单流程的异常分支"` | 剩余充足，删 |
| `"就是这个原因"` | 不变 | 不在句首插入语形态 |
| `"然后呢，我们要处理第二部分"` | **不变** | 此处"然后呢"是**语篇连接词**，删掉会丢失"接着/然后"的顺序语义 |

> B 档判定成本高、收益低。**若实现预算有限，B 档可以整档不做**——保留比删错好。

#### C 档：★永不删除（写死在禁止清单里，加单测保护）

`大概`、`差不多`、`可能`、`也许`、`估计`、`约`、`左右`、`基本上`、`应该`、`似乎`、`好像`

- **理由**：这些是**不确定性约束**，直接决定模型该给"确定答案"还是"带条件的答案"。删除属于语义漂移。
- `"大概 3 天能做完，帮我排个计划"` 必须**逐字保留** `大概` 与 `3`。
- 同理永不删：否定词（`不`/`没`/`别`/`禁止`/`避免`）、量词与数字、专有名词、`请`。

### L0-016 首尾客套收敛循环（编排步骤，无独立开关）

- **为什么需要它**：L0-010/L0-011/L0-014 每条**单次只删一块**（这是刻意的安全设计），但真实输入常常叠了三层客套：
  `"那个，麻烦你帮我看看这个 bug，谢谢！"` → 删句尾 → `"那个，麻烦你帮我看看这个 bug"` → 删"麻烦你" → `"那个，帮我看看这个 bug"` → 删"帮我" → `"那个，看看这个 bug"`。
  只跑一遍会停在中间状态。**循环到不动点**既保证删干净，又不牺牲"单次只删一块"的可回滚性。
- **算法（逐字照抄）**：

```ts
function stripTopBottomPoliteness(t: string): string {
  let cur = t
  for (let round = 0; round < 4; round++) {
    const before = cur
    cur = stripPoliteHead(cur)      // L0-010（含长度守卫）
    cur = stripSelfReference(cur)   // L0-014（含 (?!的) 守卫）
    cur = stripPoliteTail(cur)      // L0-011（含三条守卫）
    cur = cur.replace(/^[ \t\u3000]+|[ \t\u3000]+$/gm, '')  // 每轮回 L0-001 trim
    if (cur === before) break       // 不动点，收敛退出
  }
  return cur
}
```

- **为什么是 4 轮而不是 `while(true)`**：
  - 理论上"删一块 → 暴露下一块"的链条最长不会超过 3 层（首客套 + 自指 + 尾客套各一层），4 轮是安全上界；
  - **必须有硬上限**——万一某条守卫写错（例如长度守卫失效）导致"删了又长回来"，`while(true)` 会卡死渲染线程。上限让 bug 表现为"少删一点"而不是"页面卡死"。
- **`applied` 记录方式**：循环内命中的规则 ID 只在**首次**入库（`rule()` 里的 `if (c.applied.includes(id)) return` 天然去重），循环外记一条 `L0-016`。
- **幂等性**：收敛循环的输出是不动点，再跑一次首轮即 `break`，结果不变。

| 输入 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 最终 |
|------|---------|---------|---------|------|
| `"那个，麻烦你帮我看看这个 bug，谢谢！"` | 尾客套删"谢谢" | 首客套删"麻烦你" | 首客套删"帮我" | `"那个，看看这个 bug"` |
| `"你好，帮我写个请假条"` | 删"你好" | 删"帮我" | 无变化 → break | `"写个请假条"` |
| `"谢谢"` | 长度守卫全部回滚，`cur === before` → break | — | — | `"谢谢"` |

> `"那个"` 属于 L0-012 的 **B 档插入语**，默认不删（见该条"B 档可以整档不做"）。上表保留它是有意为之——**保留比删错好**。

### L0-015 输入长度兜底 · 始终生效

- **下界**：清洗后 `[...text].length < 3` → **立即返回原文**（`changed:false`，`reason:'too-short'`），不做任何后续层。
  > ★ 阈值是 **3**，不是 10（见附录 C 裁决）：写 10 会让附录 B #42 的 `"abcdefghijklmnop"`（16 字符）也变成 `too-short`，永远拿不到 `no-rule-matched`。
  > 取 3 的判定依据：`"嗯"`（1 字）与 `"。。。"`（经 L0-005 折叠成 1 字）都必须 `too-short`，而 16 字符 ASCII 必须走完全流程。
- **上界**：清洗后 `[...text].length > 8000` → 截断到 8000 个**码点** + 追加标记：

```ts
const chars = Array.from(result)
if (chars.length > 8000) {
  result = chars.slice(0, 8000).join('') + '\n\n[...内容过长已截断]'
}
```

- **必须用码点计数**（`Array.from`），不能用 `String.prototype.length`：后者是 UTF-16 码元数，会在 emoji / 生僻字（代理对）中间截断，产出非法字符。
- 截断后仍继续 L1/L2/L3（长输入恰恰是最需要结构化的）。

## 五、L1 结构层

### L1-001 任务类型识别（分析步骤，无独立开关）

**判定流程**：把清洗后的文本与下表逐行匹配 → 收集所有命中的 `TaskType` → 按 5.1.4 的优先级裁决 → 产出 `{ task, confidence, matched }`。

#### 5.1.1 关键词表（★注意宾语约束与英文词边界）

| `doc` | `(?:写\|生成\|输出\|起草\|拟)(?:一份\|个\|篇)?(?:文档\|大纲\|方案\|PRD\|周报\|汇报\|报告\|邮件\|纪要\|说明书\|总结文档)` | high |

| `qa` | `^\s*(?:what\|why\|how\|which\|when\|is\s+it\|can\s+i\|should\s+i)\b` | mid |

| `data` | `\b(?:excel\|csv\|sql\|pandas\|dataframe\|group\s*by\|join)\b` | mid |

#### 5.1.2 误判防护（★这几条是踩过的坑）

1. **单独一个"写"不构成 `code`**：`"写一段自我介绍"` 是 `general`/`doc`，不是代码。必须"编程动词 + 编程宾语"共现（见上表第一行）。`写`、`做`、`搞` 一律进黑名单当**必要非充分**条件。
2. **`优化` 是歧义词**：`"优化一下这段文案"` 是 `doc`；只有后面跟技术宾语（`性能`/`SQL`/`接口`/`代码`）才算 `code`。因此上表把 `优化` 只放进"编程宾语共现"那一行。
3. **英文必须加 `\b`**：不加时 `fix` 会命中 `prefix`，`api` 会命中 `rapid`，`ideas` 会命中 `ideas` 里的 `idea`（可接受但要注意 `idea` 单复数）。中文无需 `\b`（中文字符不构成 `\w` 边界）。
4. **疑问词与任务词共现**：`"怎么用 Python 读 excel"` 同时命中 `qa` 与 `code` 与 `data`。裁决见下。

#### 5.1.3 优先级与裁决

```
translate > summarize > code > data > doc > brainstorm > qa > general
```

- **同分规则**：先比关键词**首次出现位置**（更靠前者胜）；位置也相同则按上表优先级从左到右。
- **疑问加强**：若文本以疑问词开头且 `task !== 'qa'`，则设置 `question: true`（供 L2-002 追加"先给结论再展开"），但**不改变** `task`。这样 `"怎么实现一个 LRU 缓存"` 会被判为 `code` 且 `question:true`——正确，因为它要的是代码而不是科普。

| 输入 | 判定 | 理由 |
|------|------|------|
| `"写个请假条"` | `general` | "写"后面不是编程宾语、也不是文档宾语 → 不强行归类 |
| `"写一个二分查找函数"` | `code` | 编程动词 + 编程宾语 |
| `"优化一下这段文案"` | `doc` | "优化"后面不是技术宾语 |
| `"怎么用 Python 读 excel"` | `code` (`question:true`) | `code` 优先于 `data`；疑问标记让 L2 追加"先结论" |
| `"总结一下这篇文章"` | `summarize` | — |
| `"把这段话译成英文"` | `translate` | 最高优先级 |

#### 5.1.4 输出

```ts
function detectTask(text: string): { task: TaskType; confidence: 'high' | 'mid' | 'low'; matched: string[] }
```

无任何命中 → `{ task: 'general', confidence: 'low', matched: [] }`。

### L1-002 阿拉伯序号归一 · 开关 `normalizeList`

- **★ 两条正则，必须分开写**（这是修掉"`1.5 小时` 变成 `1. 5 小时`"的关键）：

```ts
// ① 、 与 ． 无歧义，不需要空格守卫
result = result.replace(/^[ \t]*(\d{1,3})[、．][ \t]*/gm, '$1. ')

// ② ASCII "." 有小数歧义 → 必须后跟空白。
//    ★ 必须把原空白一起吃掉（`[ \t]+` 进匹配，而不是写成 `(?=[ \t]+\S)`）：
//    替换文本自带一个空格，若原空白不被消费，`"3. 最后重启"` → `"3.  最后重启"`，
//    且每跑一遍多一个空格，直接违反 I1 幂等（见附录 C）。
result = result.replace(/^[ \t]*(\d{1,3})\.[ \t]+(?=\S)/gm, '$1. ')

// ③ 括号形态自带边界，无需守卫（中英文括号都收）
result = result.replace(/^[ \t]*[（(](\d{1,3})[）)][ \t]*/gm, '$1. ')
```

- **处理**：统一为 `'1. '`（阿拉伯数字 + 半角点 + 一个空格）。
- **作用域**：非代码段，且必须保护行内代码。
- **为什么旧实现有 bug**：`^[（(【\[]?(\d+)[）)】\]、.\s]+` 里 `[）)】\]、.\s]` 是**字符类**，`1.5 是版本号`会被匹配成 `(\d+)=1` + `[.]` + `[\s]` → 输出 `1. 5 是版本号`。字符类还包含 `\s`，对 `1  2  3` 这类输入行为也不确定。**绝不要用字符类做分隔符。**

| 输入 | 输出 | 说明 |
|------|------|------|
| `"1、先备份"` | `"1. 先备份"` | 规则① |
| `"（2）再改配置"` | `"2. 再改配置"` | 规则③ |
| `"3. 最后重启"` | `"3. 最后重启"` | 已合规，幂等 |
| `"1.5 小时就够"` | **不变** | 规则②要求 `.` 后是空白 |
| `"v0.2.0 已发布"` | 不变 | 行首非数字 |
| `"2026.10.10"` | 不变 | `.` 后是数字 |
| `"1.先备份"`（无空格） | 不变 | 规则②要求 `[ \t]+\S`；**宁可不改，也不误伤小数** |

### L1-004 顿号并列拆分 · 开关 `normalizeList`

- **触发条件（三条全满足才动手）**：
  1. 单行内 `、` 的数量 ≥ 3；
  2. 该行长度 ≥ 12；
  3. 切分出的每一项长度 ≤ 30（长句顿号多为并列从句，拆开会破坏语义 → 放弃）。
- **处理算法（共享前缀提取，避免把动词甩在第一个 bullet 上）**：

```ts
function splitEnumeration(line: string): string | null {
  const items = line.split('、')
  if (items.length < 4) return null
  if (line.length < 12) return null
  if (items.some((it) => it.trim().length === 0 || it.trim().length > 30)) return null

  // 共享前缀：第一项中"最后一个动词/介词短语"之前的部分，作为引导句
  const first = items[0]
  const m = first.match(/^(.*?)(支持|包含|包括|覆盖|分为|有|是|需要|要求)/)
  const lead = m ? m[0] : null
  const head = lead ? items[0].slice(lead.length) : items[0]
  const bullets = [head, ...items.slice(1)].map((it) => `- ${it.trim()}`)

  return lead ? `${lead}：\n${bullets.join('\n')}` : bullets.join('\n')
}
```

| 输入 | 输出 |
|------|------|
| `"支持微信、支付宝、银联、云闪付"` | `"支持：\n- 微信\n- 支付宝\n- 银联\n- 云闪付"` |
| `"甲、乙两人先去现场"` | 不变（只有 1 个顿号，未达阈值 3） |
| `"前端要考虑状态管理、性能优化、可访问性、国际化、错误边界、加载态以及骨架屏的展示时机和降级策略"` | 不变（切出的项超过 30 字，放弃） |

### L1-006 长句自动分段 · 开关 `autoSplitParagraph`（默认 `false`）

- **触发**：仅对**长度 ≥ 60** 的行生效；行内匹配 `/([。；;])[ \t]*(?=[^\n])/g`。
- **处理**：替换为 `'$1\n'`，随后 `/\n{3,}/g` → `'\n\n'`。
- **守卫**：
  - `(?=[^\n])` 前瞻：句号后**已经**是换行时不重复插空行（幂等的关键）。
  - 长度阈值 60：短句分段只会把 `"版本 1.2；来源：内部"` 拆成两行碎片，毫无收益。
  - 代码段与行内代码必须排除：代码里的 `;` 拆行会直接语法错误。
- **为什么默认关**：这是唯一会**增加行数**的 L0/L1 规则，对用户在 Markdown 里精心排版的输入破坏性最大。

| 输入（行长度 ≥ 60） | 输出 |
|------|------|
| `"先做A。再做B；最后做C。"` | 长度不足 60 → 不变 |
| 一段 80 字的连续文字含 3 个 `。` | 每个 `。` 后插入 `\n`，形成 4 行 |
| `"const a = 1; const b = 2"`（代码段） | 不变 |

### L1-007 小节标题识别 · 开关 `splitSections`

- **触发**：`/^[ \t]*(需求|功能|要求|需要|问题|背景|约束|交付|注意|目标|场景|输入|输出)[：:][ \t]*/gm`
- **处理**：替换为 `'\n### $1\n\n'`，随后 `trimStart()`。
- **★ 三条守卫（缺一不可）**：
  1. **空标题跳过**：冒号后该行剩余内容（若为空则看下一行）**必须 ≥ 3 个非空白字符**，否则不转换（`"注意：如下"` → 跳过，2 字；`"注意：第一条"` → 转换，3 字；`"注意：重构时不要动接口签名"` → 转换）。

- **作用域**：非代码段 + 行内代码保护。

| 输入 | 输出 |
|------|------|
| `"需求：登录页支持微信扫码"` | `"### 需求\n\n登录页支持微信扫码"` |
| `"注意：如下"` | 不变（内容不足 4 字） |
| `"### 需求"` | 不变（已是标题） |
| `"注意：第一条\n…\n注意：第二条"` | 只有第一处转标题，第二处保留为正文 |

## 九、不处理 / 直接透传的情况（返回原文，`changed:false`）

| # | 条件 | `reason` |
|---|------|----------|
| 1 | 输入为空或纯空白 | `empty` |
| 2 | 清洗后码点数 < 3 | `too-short` |
| 3 | 输入已是结构化提示词：含 `【任务】`/`【背景】`/`【要求】`/`【输出格式】`/`【角色设定】`，或含 `^#{1,3}\s` 标题行，或含 `You are` / `Act as` 开头的英文角色句 | `already-structured` |
| 4 | 输入含代码块（``` 围栏）**且正文占比 < 30%**：说明用户主要在贴代码，不是让你优化提示词 | `already-structured` |
| 5 | 运行完所有规则后 `text === input`（所有规则都没命中） | `no-rule-matched` |

- 情况 3/4 的判定必须在 L0 之后、L1 之前。

## 十、与 LLM 深度优化的衔接

### 10.1 两条路径的关系（与 `optimizeMode` 配置对应）

| 模式 | 路径 | 失败处理 |
|------|------|----------|
| `local` | 只跑本文档的规则引擎 | 无失败可能 |
| `llm`（默认） | 走宿主 RPC → `ctx.llm.stream()` 真改写 | 宿主把本地结果放进 `error.fallback`，客户端直接把 fallback 写入输入框并提示"LLM 失败，已降级为本地规则" |

### 10.2 本地结果作为 LLM 输入时的建议

本地引擎的输出可以前置进 LLM 调用的 user 消息，作为"已结构化的草稿"，但**推荐做法是两条路各自独立**（`llm` 模式不要把本地结果拼进 prompt）：本地改写是**规则化模板**，拼进 LLM 输入会诱导模型只做润色、丢失"扩张语义"的能力。若确实要拼接，用这段措辞：

```
以下是用户提示词的本地规则优化版本，请在此基础上进一步润色，
使其更清晰、更具体、更易被模型理解，但不要改变用户原意。
直接输出最终版本，不要解释你的修改。
```

### 10.3 语义保真的共同底线（本地与 LLM 都要遵守）

- 已明确的对象、方向、数量、范围、禁止项、术语必须与草稿一致，不得替换、扩大、缩小或颠倒。
- 无依据的具体化一律不补；必须留白的用 `[待补充:…]` 显式标注。
- 语言匹配：草稿以中文为主体则输出中文，以英文为主体则输出英文，技术术语与专有名词保留原样。

```ts
/** src/local-optimizer.ts 目标形态（规则编号与本文档一一对应） */
import type { LocalRulesConfig, RoleItem } from './config'

interface Ctx {
  text: string
  cfg: LocalRulesConfig
  role: RoleItem
  applied: string[]
  failed: Array<{ id: string; error: unknown }>   // 规则内部异常，仅调试用，绝不外泄给用户
  task: TaskType
  question: boolean
}

/** 单条规则执行器：抛错即跳过，保证"失败即降级" */
function rule(c: Ctx, id: string, fn: (t: string) => string): void {
  if (c.applied.includes(id)) return
  try {
    const next = fn(c.text)
    if (next !== c.text) {
      c.text = next
      c.applied.push(id)          // 记在 applied 尾部即天然按执行顺序
    }
  } catch (error) {
    c.failed.push({ id, error })  // ★ 不要静默吞掉：无效正则会表现为"规则莫名不生效"
  }
}

export function localOptimize(text: string, cfg: LocalRulesConfig, role: RoleItem): OptimizeResult {
  const input = text ?? ''
  if (!input.trim()) return { text: input, changed: false, reason: 'empty', task: 'general', applied: [] }

  const c: Ctx = { text: input, cfg, role, applied: [], failed: [], task: 'general', question: false }

  // ---- L0 ----
  if (cfg.cleanWhitespace) {
    rule(c, 'L0-002', normalizeInvisible)
    rule(c, 'L0-001', (t) => t.replace(/^[ \t\u3000]+|[ \t\u3000]+$/gm, ''))
    rule(c, 'L0-003', (t) => mapNonCode(t, (s) => s.replace(/[ \t]{2,}/g, ' ')))
    rule(c, 'L0-004', (t) => t.replace(/\n{3,}/g, '\n\n'))
  }
  if (cfg.filterPoliteWords) {
    rule(c, 'L0-005', foldRepeatedPunct)
    rule(c, 'L0-013', foldIntensifier)
    rule(c, 'L0-012', stripFillers)
    rule(c, 'L0-016', stripTopBottomPoliteness)  // 内部循环跑 L0-010 → L0-014 → L0-011
  }
  // ---- L0-015 长度兜底 ----
  const chars = Array.from(c.text)
  if (chars.length < 3) {   // ★ 取 3 而非 10，见附录 C 裁决：10 会让附录 B #42 永远拿不到 no-rule-matched
    return { text: input, changed: false, reason: 'too-short', task: 'general', applied: c.applied }
  }
  if (chars.length > 8000) c.text = chars.slice(0, 8000).join('') + '\n\n[...内容过长已截断]'

  // ---- 结构化判定（透传） ----
  if (looksStructured(c.text)) {
    return { text: input, changed: false, reason: 'already-structured', task: 'general', applied: c.applied }
  }

  // ---- L1 前的两个分析步骤（不改文本，只往 c 里存结果）----
  const detected = detectTask(c.text)      // L1-001
  c.task = detected.task
  c.question = detected.question
  const context = extractContext(c.text)   // L2-001 ★必须在这里跑，不能等 L1-008 才跑

  // ---- L1 ----
  if (cfg.normalizeList) {
    rule(c, 'L1-002', normalizeOrderedList)
    rule(c, 'L1-003', normalizeBullets)
    rule(c, 'L1-004', splitEnumeration)
  }
  if (cfg.autoSplitParagraph) rule(c, 'L1-006', splitLongLines)
  if (cfg.splitSections) {
    rule(c, 'L1-007', extractSectionHeadings)
    rule(c, 'L1-008', (t) => applySkeleton(t, c, context))
  }

  // ---- L2 ----
  rule(c, 'L2-002', (t) => appendOutputFormat(t, c.task, c.question))
  if (cfg.appendConstraints && cfg.constraintsText.trim()) {
    rule(c, 'L2-003', (t) => {
      const block = cfg.constraintsText.trim()
      return t.includes(block) ? t : t.trimEnd() + '\n\n' + block
    })
  }

  // ---- L3 ----
  if (cfg.enableRoleOptimization && c.role) rule(c, 'L3-001', (t) => injectRole(t, c.role))

  const out = c.text.trim()
  return {
    text: out,
    changed: out !== input,
    reason: out === input ? 'no-rule-matched' : undefined,
    task: c.task,
    applied: c.applied,
  }
}
```

辅助函数（`normalizeInvisible`、`foldRepeatedPunct`、`foldIntensifier`、`stripFillers`、`stripSelfReference`、`stripPoliteHead`、`stripPoliteTail`、`normalizeOrderedList`、`normalizeBullets`、`splitEnumeration`、`splitLongLines`、`extractSectionHeadings`、`applySkeleton`、`extractContext`、`appendOutputFormat`、`injectRole`、`mapNonCode`、`looksStructured`、`detectTask`）的具体实现在本文档对应规则条目里逐条给出。
